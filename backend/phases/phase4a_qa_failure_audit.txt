================================================================================
1. EXECUTIVE FINDINGS
================================================================================

The 11 QA_EXTRACT failures in Arm C (structure-v2 + token-aware context)
break down into three distinct root causes:

  ROOT CAUSE A — Table representation problem (4 failures, 36.4%)
    The table text is serialized as pipe-delimited rows ("Method | Result").
    The extractive QA model cannot reliably navigate row/column
    relationships in this flat text representation.  It extracts wrong
    cells, wrong rows, or headings instead of cell values.

  ROOT CAUSE B — Extractive span limitation (4 failures, 36.4%)
    Questions requiring synthesis across multiple sentences, sequential
    reasoning (lists), or multi-chunk information cannot be answered by
    extracting a single contiguous span.  The model either extracts too
    much (multi-sentence), too little (partial), or the wrong span
    entirely.

  ROOT CAUSE C — Training-data mismatch (3 failures, 27.3%)
    The model was trained on SQuAD-style prose QA.  It has limited
    exposure to table structures, list ordering, unpunctuated text,
    and academic two-column layouts.  The 50 custom academic QA pairs
    (Phase 3 training) are insufficient to cover these patterns.

No failures arise from:
  - Retrieval misses (coverage=1.0 for all QA_EXTRACT failures)
  - Context truncation (separate failure category)
  - Evidence omission (separate failure category)
  - Ambiguous questions (all questions have deterministic gold answers)

Confidence: HIGH — based on per-question context verification.

Limitation: 39 answerable questions is too small for statistical
significance.  The root cause distribution may differ on a larger corpus.

5. TABLE QA ANALYSIS
================================================================================

All 5 table-related QA_EXTRACT failures share the same root cause:
the table is serialized as pipe-delimited text ("Method | Result"),
which the extractive model treats as continuous prose.

Specific failures:

  ts_1/ts_2 (tables_small.docx):
    Table: 3 rows x 2 cols, header=["Method","Result"]
    Serialized: "Method | Result\nPCA | 85 percent\nSVM | 92 percent"
    Problem: Row boundaries are invisible to the tokenizer.  "SVM" and
    "92 percent" are adjacent tokens but the model doesn't associate
    them as a row pair.

  tl_1/tl_3 (tables_large.docx):
    Table: 31 rows x 3 cols, header=["Method","Accuracy","Runtime"]
    Serialized: "Results\nMethod | Accuracy | Runtime\n1 | 61 percent | 7 ms\n..."
    Problem: With 31 rows, the model's attention is spread thin.  The
    heading "Results" at the start gets high attention.  Method 12 and
    Method 11 are adjacent rows that confuse the model.

  mx_3 (mixed.docx):
    Table: 3 rows x 2 cols, header=["Season","Pressure"]
    Serialized: "Season | Pressure\nSpring | 1013 millibars\nWinter | 998 millibars"
    Problem: Model extracted "winter" (wrong row) for a question about
    "1013 millibars" (which is Spring).  Row-value association failure.

Diagnosis: The pipe-delimited serialization destroys row/column
structure that the extractive model needs to navigate tables.
The model has no table-awareness — it was trained on prose QA.

Confidence: HIGH — all 5 table failures have the same pattern.
Limitation: Only 7 table questions total.  More needed to confirm.

6. LIST QA ANALYSIS
================================================================================

List questions fail for two distinct reasons:

  li_1 (ordinal/sequential question):
    Question: "Which item follows draining the Vermilion loop?"
    Expected: "Remove the Helios filter"
    Predicted: "remove the helios filter torque the quokka bolts"
    Problem: The question requires understanding list ORDER ("follows").
    The model extracted a span covering two items.  Extractive QA cannot
    perform ordinal reasoning — it can only extract contiguous spans.

  lx_1 (li_2, membership question):
    Question: "What should be isolated first?"
    Expected: "Nimbus supply"
    Problem: Requires understanding list POSITION ("first").  The model
    extracted text from a different context.  In Arm C, this is now
    CORRECT (structure-v2 preserves list items as atomic chunks).

  li_3 (now CORRECT in Arm C):
    Question: "What must be confirmed in the checks section?"
    Expected: "Zephyr reading"
    Status: RESOLVED by structure-v2 (list items preserved as chunks)

Diagnosis: List questions fail when they require:
  - Ordinal reasoning ("which follows X?")
  - Positional reasoning ("which is first?")
  - Sequence understanding

These are NOT extractive QA tasks.  They require reasoning about
list structure, which the current model cannot do.

Confidence: HIGH — pattern is clear from 4 list questions.
Limitation: Only 4 list questions total.

8. TRAINING-DATA MISMATCH ANALYSIS

Training distribution:
  Phase 1: SQuAD 2.0 (87,599 samples) — prose QA, single-context
  Phase 2: SQuAD + HotpotQA + CoQA + NewsQA + TriviaQA (414,057 samples)
  Phase 3: Custom Academic QA (50 pairs) — RAG/document QA topics

What the training distribution DOES represent:
  - Prose-based factual questions (SQuAD)
  - Multi-document reasoning (HotpotQA)
  - Conversational QA (CoQA)
  - News article QA (NewsQA)
  - Trivia-style questions (TriviaQA)
  - Academic document QA (50 custom pairs)

What the training distribution DOES NOT represent:
  - Table QA (no TaPas, TAPAS, or table-structured data)
  - List/ordinal QA (no sequential reasoning data)
  - Pipe-delimited table serialization
  - Unpunctuated text
  - Multi-column PDF layouts
  - Structural element navigation (heading → paragraph → table)

Correlation with failures:
  Table failures (5/11): NO table QA training data → CONFIRMED mismatch
  List failures (2/11): NO list/ordinal training data → CONFIRMED mismatch
  Multi-chunk (1/11): HotpotQA provides some multi-hop, but not
    extractive multi-chunk synthesis → PARTIAL mismatch
  Tokenizer artifact (1/11): Not a training issue → NOT a mismatch
  Retrieval failure (1/11): Not a QA issue → NOT a mismatch

Confidence: HIGH for table/list mismatches.  MEDIUM for multi-chunk.
Limitation: Training code and full dataset details are not in the
repository.  The model card provides summary statistics only.

safe boundary.  Any positive threshold would be threshold-fitting.

Confidence: HIGH — empirical data from 39 questions.
Limitation: 39 questions is too few for reliable calibration analysis.

12. FUTURE MODEL OPTIONS
================================================================================

Option A: Better fine-tuning of current DistilBERT
  Problem addressed: Table/list representation in training data
  Evidence for: 11/11 QA_EXTRACT failures have correct evidence —
    the model architecture is capable, just undertrained on tables/lists
  Evidence against: eval_loss is 2.4x train_loss (overfitting);
    adding more data may not help without regularization changes
  Complexity: MEDIUM — retraining with expanded dataset
  New failure modes: May regress on prose QA
  Latency: UNCHANGED (same model)
  Explainability: UNCHANGED (extractive, span-based)
  Brain compatibility: FULL

Option B: Domain/structure-specific fine-tuning
  Problem addressed: Table/list-specific patterns
  Evidence for: Targeted training on table serialization patterns
  Evidence against: May not generalize; requires table QA dataset
  Complexity: MEDIUM — curated table/list training data
  New failure modes: May lose prose generalization
  Latency: UNCHANGED
  Explainability: UNCHANGED
  Brain compatibility: FULL

Option C: Larger extractive QA model
  Problem addressed: Capacity limitation for complex reasoning
  Evidence for: DistilBERT is a compressed model; full BERT or
    DeBERTa may perform better
  Evidence against: +2-5x latency; +2-4x memory; diminishing returns
  Complexity: HIGH — model replacement, retraining
  New failure modes: Different attention patterns
  Latency: INCREASED (2-5x)
  Explainability: UNCHANGED (extractive)
  Brain compatibility: FULL (same interface)

Option D: Generative QA
  Problem addressed: Multi-chunk reasoning, synthesis, tables
  Evidence for: Generative models can synthesize across chunks;
    can handle tables as structured input
  Evidence against: Loses extractive traceability (answer may not be
    a span in context); requires different evidence gate logic;
    higher latency; hallucination risk
  Complexity: HIGH — new model, new gating, new evidence verification
  New failure modes: Hallucination, ungrounded answers
  Latency: INCREASED (3-10x)
  Explainability: REDUCED (generative, not span-based)
  Brain compatibility: PARTIAL (evidence gate needs redesign)

Option E: Hybrid extractive + generative
  Problem addressed: Best of both — extractive for simple, generative
    for complex
